# Test CPU and flakiness review (2026-09-29)

Branch `perf/hot-tests`. The owner saw tests pinning cores. This review finds
where the time goes, fixes it, and explains the load-only failures. All
numbers come from a debug build on a 12-core machine. `measure.py` reports
wall time, rusage and `/proc/self/io` deltas for the test process and the
children it reaped. Stacks were sampled by running the test binary as a
child of gdb and interrupting it every 0.5–5 s. ptrace settings were not
changed.

## 1. `planning_gate_ten_logical_workers` (tests/factory_harness.rs)

| | wall | user+sys | rchar | read syscalls | wchar |
|---|---|---|---|---|---|
| before | 401.9 s | 359 + 37 s | 124.2 GB | 30.3 M | 1.08 GB |
| after | 14.5 s | 12.4 + 2.0 s | 2.16 GB | 0.53 M | 1.08 GB |

**Where the time went.** 49 of 57 stack samples (86%) were in
`SqliteStore::integrity_check ← SqliteStore::open ← worker_snapshots_for`.
Another 5 were in `connect` under the same caller. So 95% of the time went
to the test fixture, and admission used almost none of it.
`worker_snapshots_for` opened a new `SqliteStore` for each missing
(task, profile) memory snapshot. The test has 10 queued tasks and 301 retained
profiles, so the first pass opened the store 3,010 times. Every
`SqliteStore::open` runs `PRAGMA quick_check` and `PRAGMA foreign_key_check`
over the whole ~25 MB store, which comes to about 124 GB of reads. The
hypothesis "admission full-scans capability history" is wrong. The test
itself shows that admission SQL work is flat, at 4,202 VM steps both before
and after the 30,000 retained `capability_evidence` rows. Those lookups are
served by `capability_evidence_by_profile(profile_digest, level)` and
`_by_kind`, and admission opens through `open_scoped`, which skips the
whole-store check. Production needed no index or migration.

**Fix (test fixture only).** `worker_snapshots_for` opens one `MemoryStore`
per pass and reuses it for every snapshot it creates. It still creates every
snapshot, including those for the ineligible historical profiles. The
integrity check still runs once per pass. All assertions are unchanged,
including the VM-steps bound. Every other `worker_snapshots` user in the
file benefits too.

## 2. Flaky `canonical_worker_queue_rotates_beyond_its_inventory_limit`

I reproduced it with 4 concurrent copies of the test plus the binary's
unit suite at 12 threads. It showed two separate causes.

**(a) `state store: Io("interrupted")` at line 79 (`reads.poll`). 2 of 4
copies failed.** `observation_head` reads the head through a new read-only
connection under a 100 ms wall-clock budget. When the deadline passes, the
progress handler returns SQLITE_INTERRUPT. Each new connection has to load
the whole schema: 889 objects (178 tables, 290 indexes, 419 triggers, about
200 KB of SQL). With the system SQLite that costs 6.5 ms median (10 ms p99)
per connection, measured. `PRAGMA user_version` alone costs 0.13 ms. On an
idle machine no head read took more than 20 ms. The test makes 3,096 such
reads (129 projects × 24 passes). On an oversubscribed machine, one thread
descheduled for more than 100 ms fails the poll, and the test `unwrap`s
every poll. In production an overrun marks the poll `unknown`, and the
ticker retries it on the next pass. That is the intended behaviour.

*Fix:* the budget is now the constant `HEAD_READ`, which stays 100 ms in
production and is 10 s under `cfg(test)`. This test-only increase is
justified: the unit tests assert rotation, offer/pending bounds and fencing,
not read latency. The job-side head read in `collect` uses the same
constant. Integration tests run the normally built binary and keep 100 ms.

**(b) `another operation owns lock <root>/<project>/.state/lock; retry`.**
This is the steward's line-76 failure: migration `apply` while the 129
projects are created. I captured the same failure in `Fixture::new`
(line 7). `Project::lock()` released the legacy per-project flock only by
closing its descriptor. A child forked by any other thread holds a copy of
the open file description until it execs, so the flock outlived the
release. The following non-blocking `exclusive_file(".state/lock")` in
`migration::apply` then failed. `execution_guard::LockFile` already
documents this hazard and unlocks explicitly. `ProjectLock` did not.

I checked the mechanism with a Python model (flock, release, then an
immediate non-blocking relock while 4 threads fork+exec). Releasing by
close caused 4,050 spurious "owned" failures out of 5,000; explicit unlock
caused 0. This is also a production race, because the ticker is
multi-threaded and spawns while it holds `project.lock()`.

*Fix:* `Drop for ProjectLock` calls `unlock()`. `ArtifactLock::Canonical`,
which takes the same `.state/lock`, does the same.

## 3. Other load-only failures seen while reproducing

- `routine_jobs::…running_job_preserves_control_lane_and_cancellation_drains_without_certifying_cleanup`
  failed with `escaped` existing. Its detached child wrote `escaped` 0.8 s
  after starting. Under load, the test's steps between `started` and
  `pool.stop` took longer than that, so the child wrote the file before
  cancellation. *Fixed:* the child now waits for a `release` file that the
  test writes only after cancellation, then sleeps the same 900 ms. A child
  that survived cancellation still writes the file, and the result no longer
  depends on the load.
- `canonical_worker.rs::a_proven_worker_end_keeps_the_project_admitted_but_an_unexplained_pane_loss_pauses_it`
  (steward's request) failed in 4 of 4 runs under load. This is **not** the
  flock-by-close cause.
  - 3 runs failed at line 244, the 120 s wait for `Running`. The ticker log
    showed only lock contention inside the ticker: "barrier stop / wait /
    replan / verification / integration job service: root maintenance or
    exclusive external operation is active; retry", "another operation owns
    lock .state/effect.lock", and the launch job's "another operation owns
    lock root/.execution.lock".
  - 1 run failed at line 619: the ownership claim was not retired within
    the fixed one `pane.list` pass plus one pass.

  These locks are the explicit-unlock `LockFile` and `ProjectGuard` locks,
  contended by the ticker's own try-lock services, the root-exclusive launch
  and the transferred supervisor locks. What I did change here: the test's
  own wait loop polled a full integrity-checked snapshot every 20 ms. It now
  backs off to 250 ms, which cut the test's CPU from 43.9 s to 23.5 s and its
  wall time from 54 s to 43 s, and reduces the load it adds.

  **Cause and fix (lock-retry progress card, `fix/lock-retry-progress`).**
  Reproduced with 36 busy loops on 12 cores: 0 of 5 runs passed, all at the
  120 s wait for `Running`. Pass-by-pass ticker logs showed two separate
  problems.

  - *The launch lost the root to the ticker's own services, every time.*
    The launch job is admitted at the end of pass N and takes the exclusive
    root (`root/.execution.lock`) on an executor thread. Under load pass N
    already took more than the 250 ms cadence, so pass N+1 started at once.
    Its five controller services (barrier stops, waits, replans, verification
    jobs, integration jobs) each take project ownership, which holds the root
    shared, and they took it before the launch thread did. The launch failed
    ("another operation owns lock …/.execution.lock"), backed off 1 s, the
    maintenance turn ran an observation (the services then failed on
    `.state/effect.lock`), and the launch was admitted again into the same
    race. The logs show ten such cycles in a row before one launch won.
    The launch also takes the root afresh at each durable stage (resource
    creation, worktree preparation, gate release, naming), and a service
    landing in one of those gaps failed a launch that was 12 s in. Repeated
    losses used up the launch lease, and the attempt went to the termination
    path and never ran.

    *Fix:* while a root-exclusive effect (launch, brief, termination) is
    admitted, and until the pass that drains it, the ticker skips those
    services and the migrated memory-review delivery, which also takes
    project ownership. They report pending work, so the ticker stays awake.
    They run in the next pass after the drain, before anything new is
    admitted, so the effect and the services take turns. This extends the
    existing rule that keeps observation jobs off the root while an
    exclusive effect is pending (`canonical_controller::finish_poll`,
    `ticker::tick`). The staged adapters also take the root through
    `RootGuard::exclusive_by`. It retries a lost try-lock every 10 ms for up
    to 2 s, never past the effect's deadline or its cancellation. A short
    shared holder, such as a CLI command, then delays a stage rather than
    failing the job. The locks, their order, fencing and maintenance
    exclusivity are unchanged; only the wait is new.
  - *The line-619 failure was not lock contention.* The retirement comes
    from the observation job that sees the pane gone. A pass admits that job
    at its end and publishes the metrics file before the job runs. The test
    stopped the ticker as soon as it saw the `pane.list` request, and then
    right after the next pass. Stopping cancels in-flight work, and the logs
    show the observation ending with "state store: Cancelled" both times.
    The test now waits for the retirement commit, and then for a later
    observation commit, each within four passes. The margin covers passes
    whose 100 ms observation-head read overruns under load, which then offer
    no observation (see the per-connection schema-load follow-up).

  New regression: `canonical_worker.rs::a_launch_reaches_running_while_another_holder_takes_the_shared_root_intermittently`.
  A thread holds the shared root for 300 ms of every 400 ms while the ticker
  launches and briefs a worker. The test asserts `Running`, that no effect
  lost the root, and that no service contended with an admitted effect. It
  does not depend on machine load. With both fixes reverted it did not
  reach `Running` in 120 s on an idle machine. With only the bounded wait,
  the service assertion fails.

  Pass counts under 36 busy loops on 12 cores: before the fix 0 of 5
  (all at the `Running` wait), after it 5 of 5. In five earlier
  instrumented runs of the same fix, no ticker log had a launch losing the
  root or a service contending with an admitted effect. Two of those runs
  failed at the retirement step with a two-pass bound, which led to the
  four-pass margin above.
- Wall-clock bounds that were exceeded only at 3× oversubscription
  (36 test threads on 12 cores). Not changed:
  `local_reports::…retained_unconsumed_hashes_have_a_global_cache_bound`
  (3 s wait), `artifacts::live::…report_and_library_each_have_their_own_byte_budget`
  and `…live_section_limits_do_not_expand_the_combined_preservation_limit`
  ("artifact source read deadline elapsed"),
  `canonical_post_probe_sql_cannot_restart_its_budget` (700 ms budget), and
  `canonical_worker_and_routine_admission_take_separate_project_turns`.

## 4. Second CPU hog: `cli::ticker_auto_integrates_two_results_serially_and_recovers_stale_and_crash`

Measured alone: 318 s wall, **174.7 s user + 46.0 s sys, 147.6 GB read,
36.1 M read syscalls**. `VerifyFixture::wait` evaluated its predicate every
10 ms. The predicate calls `runtime::snapshot`, which is a full
`SqliteStore::open` integrity check plus a full snapshot read, and it ran
for minutes while the ticker it waited on advanced in 15 s passes.

*Fix:* the wait loop backs off from 10 ms to 250 ms. The predicate and
deadline are unchanged. After the fix: 316 s wall (bound by ticker passes),
30.4 s user + 9.5 s sys, 36.1 GB read. `canonical_worker.rs` got the same
change (§3).

## 6. Finding for later (not changed)

Every fresh connection pays about 6.5 ms of schema load (889 objects, 419 of
them triggers, many of them per-table immutability guards). Hot paths that
open a new connection on each ticker pass pay this per project per pass,
and some of them do it more than once: `observation_head`, the canonical job
head read, and `wake_enabled`. At 129 projects that is about 0.8 s of CPU
per pass just to parse schema. Options:

- keep a per-project connection in the ticker, if the sidecar checks can be
  preserved;
- merge the immutability triggers in a future migration.
