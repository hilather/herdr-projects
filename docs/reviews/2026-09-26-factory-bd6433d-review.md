Findings, in priority order:

1. **[P1] Dependencies in the signed task contract do not constrain admission.**

   Locations: [contract parsing](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/domain/factory.rs#L468), [contract installation](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/store/results.rs#L647), [candidate selection](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/admission.rs#L79).

   Contract parsing validates `dependencies`, but retains them only in the raw signed document. Installation does not reconcile them with `task_dependencies`; admission reads the independently maintained queue edges. A task queued without edges can acquire a new signed contract requiring a predecessor and still be reserved immediately. The regression probe creates two queued tasks, installs revision 2 requiring the second task's verified result, confirms there are zero verified results, then successfully reserves the dependent through the existing exact-grant path. The launch grant does not incorporate the missing prerequisite. This violates F1.5/F2.2 and the catalog's requirement to revalidate the exact task contract at reservation. Persist and bind contract dependencies, reject queue/contract disagreement, and recheck the contract revision in the reservation transaction.

2. **[P1] Passing the wrong verification policy releases a dependency.**

   Locations: [consumer selection and satisfaction publication](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/store/satisfaction.rs#L161), [dependency schema](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/migrations/0030_dependency_satisfaction.sql#L3).

   `record_verified_result` satisfies every matching predecessor/edge-type pair without checking the policy required by the consumer. `task_dependencies` has no policy reference, and `load_verified` reduces a result to its task ID. The probe installs a consumer contract requiring `required-tests`, runs the real isolated verifier successfully under a different `builds` policy, and observes a valid dependency satisfaction although `required-tests` never ran. This does not depend on forged verifier rows. Store the required policy/revision or digest on the edge and validate it both when publishing and when consuming satisfaction, including the late-edge/backfill path. F1.4 and catalog 14 explicitly require policy-bound evidence.

3. **[P1] The replacement hot-path reader is still unbounded in historical work.**

   Locations: [targeted reader](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/store/targeted.rs#L329), [unfiltered loads](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/store/targeted.rs#L347), [automatic admission snapshot](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/admission.rs#L236).

   `read_targeted_hot_path` passes no read budget and loads all tasks, attempts, operations, deliveries, attempt inputs, and approvals. The underlying readers have no active-state predicates or page limits. It computes candidate/blocker data, discards it, and returns only the schema number. `due_effects` additionally searches the entire operations vector for each delivery. Automatic admission still calls `read_snapshot(None)` on each enabled wake. Consequently retained history continues to increase foreground work and can delay dispatch/cancellation; F4.2 is not implemented by changing the mode constant. `hot_path_rows_decoded` measures a different active-work-page query, so that metric does not expose the scans. Use bounded indexed reads at the actual decision points and propagate their deadlines; measure the work those calls perform.

4. **[P2] Wait replay loses future wakes and accepts unrelated wakes.**

   Locations: [terminal replay shortcut](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/store/plans.rs#L703), [unfiltered event scan](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/store/plans.rs#L722).

   The first `replay_wait` permanently changes a wait to `replayed`, even if no matching wake exists. Later calls return the stored answer and never inspect new events; registering the same task/attempt/condition/plan also returns the same wait. A normal poll before child completion therefore loses the later wake. Separately, the scan reads only sequence and kind, so any `wait.wake` after the cursor wakes every wait regardless of event entity. Two regression probes reproduce both behaviors. Keep a live subscription cursor until the condition is resolved, filter relevant identities, and deduplicate individual events rather than closing the subscription after its first read. The new wait APIs also lack production call sites/event producers, so F2.4 remains incomplete even beyond these state-machine defects.

5. **[P2] SHA-256 Git repositories cannot be materialized for verification.**

   Location: [checkout initialization](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/verification/checkout.rs#L67).

   Contracts and submissions explicitly accept `object_format: sha256`, but the verifier creates its disposable repository with plain `git init`. Its sanitized environment defaults to SHA-1, and `materialize` does not receive the source object format. Copying valid SHA-256 objects into that repository then fails at checkout. The probe creates a real SHA-256 repository and supplies its complete loose-object set; materialization fails with `git checkout: --detach does not take a path argument '<64-character OID>'`. Pass the bound object format through initialization and test both formats. This is required by the catalog's explicit Git-OID compatibility rule.

6. **[P2] Migration regression fixtures were not updated for schemas 27–41.**

   Location: [published-v2 migration fixture](https://github.com/hilather/herdr-projects/blob/bd6433d4d488d5d6b37701ce5707b580f076b752/src/migration/tests.rs#L250).

   Several tests create the newest store and simulate an older schema by dropping tables only through schema 26. They leave newer tables in place, then rerun migrations that attempt to create those tables. A standalone rerun of `published_v2_store_upgrades_explicitly_without_losing_migration_identity` deterministically fails with `table verification_runs already exists`; its final assertion also still expects schema 26. Similar failures appear across the upgrade tests. This proves broken compatibility validation, not that a genuine historical schema necessarily fails to migrate. Build fixtures from the historical migration prefix, update current-version expectations, and restore passing upgrade checks before claiming F0.2/F5.5 acceptance.
